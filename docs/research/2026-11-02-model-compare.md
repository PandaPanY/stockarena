# 换一个模型做 AI 优化，结果会不一样吗

日期：2026-11-02。实验设计：[docs/prereg/2026-10-31-model-compare.md](../prereg/2026-10-31-model-compare.md)（运行前写定，含变更记录）。代码：`backend/app/quant/model_compare.py`（结果 `data/research/model_compare.json`）。

这是《[让 AI 改了 472 个策略版本之后](2026-11-01-ai-versions.md)》的补充实验。那份报告里的研究混用了三种模型，这里把模型作为唯一的变量：两个模型各拿一套风格库的 7 条初始策略，用完全相同的提示、检验区间、升级门槛与交易成本，各优化 10 轮。

- **DeepSeek**：云端，`deepseek-flash`，按量计费。
- **本地 Qwen**：Qwen3.8 flash next 的社区微调版（`davidau-qwen3.8-flash-next-abliterated-turbo-brilliance-iq3_s`），llama.cpp 兼容服务，一张显卡。

## 结论

**看不出差别。**

- 按事先写定的规则，要在至少 6 种风格上留出期提升都更高，才能说某个模型「可能更好」。实际结果：本地 Qwen 赢 2 种，DeepSeek 赢 1 种，另外 4 种两边一样。
- 两个模型的行为也很像：都能稳定输出合法的候选，升级次数相近（4 次和 3 次），开发期提升明显大于留出期提升。
- 在指数择时上，两个模型各自独立提出了**同一个改动**：空仓时把国债 ETF 换成黄金 ETF。提出时间相差 3 小时，规则一字不差，开发期和留出期的结果也完全相同。

主报告的结论在这里同样成立：开发期提升的平均值是留出期提升的 10 倍以上。换模型改变不了「在开发期噪音里打转」这件事。

## 汇总

| 指标 | DeepSeek | 本地 Qwen |
|---|---|---|
| 轮数（可用） | 70（64） | 70（60） |
| 不可用轮次的原因 | 6 轮：账户余额用完（402） | 10 轮：显卡故障导致服务无响应 |
| 候选（重复） | 192（0） | 178（1） |
| 升级 | 4 | 3 |
| 开发期夏普提升（7 种平均） | +0.21 | +0.16 |
| **留出期夏普提升（7 种平均，主要指标）** | **+0.02** | **+0.01** |
| 留出期提升更高的风格数 | 1 | 2 |
| 花费 | 3.04 元 | 0（电费另计） |
| 每轮耗时（前 4 种风格，无故障） | 约 1.2 分钟 | 约 3.1 分钟 |
| token（输入 / 输出） | 50.5 万 / 63.4 万 | 56.3 万 / 54.3 万 |

两边不可用的轮次都不是模型本身的问题（账户余额、显卡故障），没有一轮是因为模型输出格式错误。处理方式见实验设计的变更记录：失败的轮次计为不可用、不重跑，被打断的运行补到满 10 轮。

## 怎么理解

- **只跑了一次。** 每个模型、每种风格各 10 轮，同一个模型重跑一遍，结果也可能不同。表里任何一格的差别都不该当成模型能力的差别。
- **7 次升级里 5 次留出期没变差**，比主报告的 6 次里 1 次好。但样本太小（7 次，其中 2 次是同一个改动），而且这些是全新的策略：累计检验次数少，升级门槛比用了很久的策略宽松。均值回归两次都是开发期大幅提升、留出期明显变差，和主报告里均值回归 v2 的情况一样。
- **两个模型想到同一个改动**，说明在给定的报告和规则空间里，「显而易见」的改进并不多，模型差别不大也就不奇怪了。用黄金替代国债做避险，和[跨资产配置研究](2026-10-31-cross-asset.md)的方向一致。
- **本地模型够用。** 质量看不出差别，速度慢 2～3 倍，不花钱。但要承担本地服务的稳定性：这次显卡卡死让服务器约 30 小时无响应。

## 复现

在部署了 StockArena 并配置了两个模型供应商的实例上：

```bash
cd backend
uv run python -m app.quant.model_compare setup <供应商 id> <供应商 id>
uv run python -m app.quant.model_compare run
uv run python -m app.quant.model_compare report
```

运行期间不要重启后端（后端启动时会把未完成的研究标记为中断）；中断后再次 `run` 只补剩余轮数。
